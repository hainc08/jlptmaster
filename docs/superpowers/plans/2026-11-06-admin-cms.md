# JLPT Master Admin CMS Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Turn the approved-for-review prototype (`docs/design/admin-cms/index.html`) into a real, role-guarded Admin CMS: dashboard, members, levels, system settings (incl. roles matrix) and audit log.

**Architecture:** New route group `app/admin/(cms)/` with its own shell (sidebar + topbar) and pages; thin route handlers in `app/api/v1/admin/{dashboard,members,levels,settings,audit}` that call feature services in `src/server/services/`. Authorization is a per-module permission lookup (`RolePermission` table) enforced in every route handler; the UI only hides what the API already forbids. Every mutation writes an `AuditLog` row with redacted before/after.

**Tech Stack:** Next.js 16.4 (App Router, `proxy.ts`), React 19, Tailwind 4, Prisma 6 (`mysql` provider → MariaDB), zod 4, Vitest 3 (+ Testing Library), Playwright.

**Spec:** `docs/design/admin-cms/index.html` (visual/behavioral reference), `SPEC.md` §§ 4, 8, 9, 10 (roles, API rules, admin ops), `AGENTS.md` (gates).

## Global Constraints

- **Approval gates (AGENTS.md):** Task 1 is docs only and ends with a STOP. Tasks 2+ must not start until the owner records approval in `docs/phase-state.yaml` for (a) the new UI scope and (b) the API/DB contract. Never self-approve.
- MariaDB only, Prisma provider `mysql`; no PostgreSQL. IDs follow existing style (`@db.Char(36)` uuid; `JlptLevel.id` is `Char(2)`).
- Read `node_modules/next/dist/docs/` for the relevant API before writing route/page code (Next 16 differs from training data).
- TDD per task: failing test (RED) → minimal code (GREEN) → refactor → run regression (`npm test`, `npm run typecheck`, `npm run lint`); paste real command output into `docs/phase-log.md`.
- N5 first: only N5 is `PUBLISHED`; N4–N1 are structural (DRAFT / COMING_SOON). Never invent official JLPT scoring; exam scores are shown as percentages.
- Do **not** modify or replace existing `/admin`, `/admin/content`, `/admin/exams` pages. New screens live at `/admin/dashboard`, `/admin/members`, `/admin/levels`, `/admin/settings`, `/admin/audit`.
- Design tokens copied from the prototype `:root` block: primary `#3730A3`, accent `#C0331B`, card radius 12px, 8px grid, fonts Noto Sans + Noto Sans JP. WCAG AA. Sidebar collapses to icon rail at ≤768px. No dark mode.
- API errors use the existing envelope `{ error: { code, message } }`; auth failures go through `authErrorResponse`.
- Commits: one per task, conventional style (`feat(admin): …`), end with the Co-Authored-By line given by the harness.

## Review Focus

1. A Support/Editor user calling `/api/v1/admin/members` (or any module they lack) by direct URL → must get 403, not data. (Task 3, 5)
2. An admin suspending/deleting **themselves** or the last OWNER, or a role-matrix edit that removes `settings` from ADMIN/OWNER (lock-out) → rejected with 409. (Task 5, 7)
3. CSV export: names/emails containing commas, quotes, newlines, Japanese text, and cells starting with `= + - @` (formula injection) → quoted, `'`-prefixed, UTF-8 BOM. (Task 5)
4. Search/filter input: `%`, `_`, empty string, 500-char query, page beyond last page, `perPage` > 100 → safe, empty page or clamped, never a 500. (Task 5)
5. Audit before/after must never contain `passwordHash`, session tokens or reset tokens; enabling a level that is not `PUBLISHED` must be rejected. (Task 4, 6)

## Open questions for the owner (answer in the approval step)

- **Roles:** SPEC has STUDENT/EDITOR/ADMIN; prototype has Owner/Admin/Content Editor/Support. Plan adds `OWNER` and `SUPPORT` to `Role`. Is that approved?
- **Member "Delete":** prototype copy says permanent. Plan implements *anonymize + `deletedAt`* so exam-attempt history is preserved (SPEC: edits must not rewrite attempt history). Approve, or require hard delete?
- **Settings are stored but not yet consumed** by the exam engine (`exam-service.ts` has its own limits). Wiring them is out of scope here; confirm.
- **Plans** (Free/Standard/Premium) have no billing backend; they are admin-assigned labels with `planExpiresAt`.
